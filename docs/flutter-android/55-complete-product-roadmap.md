## 1. 产品定义

KhmerX 是一套**面向公众借款人的完整小贷产品 App**（Android 原生）：从注册、实名、申请、签约、审批，到放款、还款、结清、再借，以及通知、客服与账户合规，覆盖借款人的整个生命周期。

- 业务规则由服务端驱动；金额为整数分；请求幂等；无离线写队列；安全日志与安全存储——这些**约束不变**。
- 后台（运营、机构、财务、贷后）继续是 Web，不在 App 范围。
- 注册/登录**公开**（`54`）；公司/机构是服务端的分区与运营主体概念，**DEC-1 = A：只有一个当前运营机构（单一公开运营工作区）**，对客户**完全不可见**（不展示 CompanyId、机构选择、机构二维码，也不要求邀请链接）；租户基础设施作为休眠资产保留。

## 4. 新阶段说明（User Outcome / Included / 前置 / 未决）

### P6 — Repayment（DEC-2 = C：混合；**两个录入渠道，一个账本**）

> **冻结的架构决策：P6-A 与 P6-B 是两个还款录入渠道，不是两套会计系统。二者最终必须写入同一个权威还款账本（ONE authoritative repayment ledger）。** 不得出现"人工余额 vs 自动支付余额"两个真相来源。账本决定：已还金额、剩余金额、结清、还款历史、凭证引用。客户端对任何还款余额都不具权威性。

**最终产品**：主路径 = KHQR/Bakong 自动还款；兜底 = 线下转账 + 员工确认。**顺序：P6-A 先于 P6-B。**

#### P6-A — Offline Transfer + Manual Confirmation
- **客户**：查看应还金额 → 查看转账指引 → 完成线下转账 → （若 Contract 要求）可选提交参考号/凭证 → 等待员工确认 → 看到还款确认 → 看到更新后的剩余金额。
- **后端**：人工还款登记；员工确认；写入**同一还款账本**；凭证/参考号；幂等记账。
- 员工确认**不得**直接改写任意余额，必须产生**可审计的还款过账**。

#### P6-B — KHQR/Bakong In-App Payment + Automatic Reconciliation
- **客户**：选择应用内支付 → 创建支付 → 完成 KHQR/Bakong 流程 → 收到 pending/成功/失败 → 看到已对账的还款 → 收到凭证。
- **后端**：支付意图（payment intent）；通道回调；回调去重；自动对账；幂等还款过账（同一账本）。

- **共同前置**：**CR-004**（共享账本、金额/对象绑定、回调安全、幂等）；取代当前硬编码的 `CUSTOMER_SETTLEMENT_FORBIDDEN`（须有真实核验，禁止客户端自报 `paymentVerified`）；在 CR-004 **实施并验收完成之前，客户 `repay` 保持被阻断**。

### P7 — Disbursement & Receiving Account（DEC-3 = APPROVED）
- **用户结果**：借款人在放款前确认最终收款账户，随后看到放款指令的状态（pending / processing / confirmed / failed / returned / cancelled）与凭证。
- **冻结**：对客户**取消 `wallet`、`withdraw`、"提现"**，改为**直接放款到收款账户**；内部钱包/结算账可作为内部会计保留，但不是客户产品概念。
- **客户流程**：KYC 收款账户 → 贷款获批 → 最终收款账户确认 → 放款指令 → pending/confirmed/failed/returned。
- **收款账户锁定（冻结）**：一旦创建 **Disbursement Instruction**，该次放款的收款账户**不可变**；创建之前，账户仅可在已定义的校验/KYC 策略下修改；创建之后**不允许普通客户编辑**，任何更改须经后端 Contract 明确定义的取消/重发/受控变更流程；**禁止静默替换**。
- **前置**：**CR-005**（放款指令、收款账户引用与锁定、状态机、`funding.confirmed`/`payment.failed` 消费、凭证）。

### P8 — Notifications, Due & Overdue
- **用户结果**：审批结果、放款、到期前提醒、逾期提醒即时到达；App 内能看到逾期信息。
- **Included**：推送注册与权限、通知偏好、站内通知（仅当有后端数据源）、到期/逾期展示。
- **前置**：**CR-006**：设备令牌注册/注销、推送提供方（FCM 等，DEC-4）、按事件触发的发送与去重；**CR-007**：**逾期状态/天数、罚息与费用规则**（今天不存在；产品先不能凭空设计 overdue，须有后端 Contract）。
- 注意：铃铛/消息中心仅在有真实通知数据后才规划，禁止复制 H5 的死 UI。

### P9 — Support & Account Compliance
- **用户结果**：能联系客服、查看帮助；能删除账户并撤回授权；协议以本人语言展示。
- **Included**：客服入口（渠道 DEC-7：Telegram 机器人/电话/表单）、帮助中心（静态或服务端）、账户删除（应用商店政策与金融数据保留期的冲突需法务）、数据授权管理、协议多语言。
- **前置**：**CR-008** 账户删除/匿名化（与 KYC/贷款/审计保留规则对齐，审计表不可变）；**CR-009** 协议多语言（法务提供官方译文，Android 不自译）；客服渠道配置。

### P10 — Institution Routing（**HOLD / CONDITIONAL**）
- **DEC-1 = A，不进入关键路径、不排期。** 仅当未来有决策取代 DEC-1（多机构撮合 / 机构专属渠道）时才激活；休眠的租户/Cookie/候选/深链/扫码基础设施保留以备恢复。

## 8. 关键路径与风险
1. **真实资金不可在没有支付通道与核验的情况下上线**：当前 `paymentVerified`、`wallet`、全局机构回调密钥均为测试级（审计 H-2、M-10）。
2. **DEC-1 已定为 A（单一运营机构）**；仍需避免扩大 `(owner, phone)` 耦合，保留未来迁移缝（ARC-3）。
3. **逾期无后端定义**：不能由客户端发明 overdue；先 CR-007。
4. **Mini App 专属能力不能照搬**：Telegram 提醒需要 `initData`，Android 必须有自己的通知方案（P8）。
5. **后台安全债**：审计的高危项应在 R3 之前关闭。

## 9. 与现有约束的一致性
- Cookie 会话 + Origin，不引入 Bearer（推送令牌注册走现有会话接口，不是新认证体系）。
- `repay`/`withdraw` 在 CR-004/CR-005 之前保持 BACKEND BLOCKED；P6/P7 由新 Contract 解锁，**不得**回到"客户端功能开关"的旧做法。
- 所有金额/费用/逾期由服务端给出；客户端只做显示派生（如 `max(0, amount+fee−paid)`）。
