## 5. Trace implementation (A2, frozen rule)
- Trusted outermost ingress (standalone gateway) is the **only** `traceId` generator. Generated once per request at the top of the handler; used by both success and catch paths.
- Inbound `X-Request-Id` / `x-khmerx-trace-id` are **untrusted**: stripped from forwarded headers; at most kept as a bounded log-only `client hint` (`[trace] client hint ignored`), never echoed, never used for decisions.
- Worker adopts the forwarded internal `x-khmerx-trace-id` **only** when `x-payease-identity-proof` (gateway HMAC) is present; otherwise (hosted / direct Worker as ingress) the Worker `serverTraceIdFor` generates its own `req_<…>`.
- Body `requestId` (business idempotency key) is distinct from `traceId`; a static scan prevents them being conflated (envelope only sets `traceId`, never reads request `requestId`).
- Response header `X-Request-Id: <traceId>` and error body `traceId: <same>`.

## 6. Typed ApiError (A3)
`ApiError(code, {safeMessage?, details?})` — `status`/`retry`/`ui`/`log` derived from the registry; `status` cannot be overridden at construction (one code == one status). `code` must be a registered code or the constructor throws (unregistered code is a development-time P0 signal). `message` is a user-safe compatibility fallback (`safeMessageByCode`); it never carries internal exception/stack/SQL text.

## 9. `REQUEST_FAILED` migration (A7)
Staged order followed. The primary migrated paths (`/api/h5/state` POST and `/api/state` catch) no longer generate `REQUEST_FAILED`:
- `lib/domain.ts` folded domain errors → explicit canonical `ApiError` codes (§6 mapping).
- `lib/store.ts` CAS collision → `REVISION_CONFLICT`.
- `/api/h5/state` inner fold removed; errors flow through `classify`.
Known domain validation failures are therefore **not** converted into 500s (they become their canonical retry/status). `REQUEST_FAILED` remains as a defined registry code and compatibility alias for any still-unmigrated sub-path; new code must not emit it (static-scan guarded, T10/T11).

## 10. `UNCLASSIFIED_ERROR` handling (A6)
Untyped/unexpected exceptions reaching a unified exit are classified as `kind:'internal'` → public `500 INTERNAL_ERROR` with `traceId`; `UNCLASSIFIED_ERROR` exists only as an internal observability classification (sink `unclassified(route)`), never in a public response. Direct regression: `tests/error-envelope.test.mjs` T7 asserts a bare `Error` produces public code `INTERNAL_ERROR` (not `UNCLASSIFIED_ERROR`) and no internal text leak (T8).

## 11. Details whitelist (A9)
`ApiError` constructor allows only keys in `DETAILS_ALLOWED_KEYS` (`field`, `missing[]`, `limitCents/minCents/maxCents`, `currentStatus`, `reason`, `expiresAt`, `retryAfter`) and strips `reason` values not allowed for the emitting code (cross-code reason asserted/rejected). No SQL / employee identifiers / secrets / provider raw errors / full account or phone data are placed in `details`. Sensitive-field regex scan in `error-envelope.test.mjs` T8. Asserts (T3) that `{employeeId:'x'}` is stripped and a bogus `reason` is stripped.

## 12. Retry semantics (A5)
Registry provides per-code `retry` metadata (layering only — no generic automatic retry). Global rule enforced/documented: GET/HEAD may retry per classification (bounded); POST/PUT/PATCH/DELETE never auto-retried unless the endpoint contract guarantees idempotency AND the same idempotency key + same payload are reused; `INTERNAL_ERROR` is `CONDITIONAL` and never authorizes blind mutation retry. `error-registry.generated.json` documents this and asserts 0 `READ_SAFE` mutation codes (T12). Transport retry policy (Android `retry_policy.dart`) is kept separate from business idempotency.
