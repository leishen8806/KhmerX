## 1. 目标与范围

### 1.1 目标
为 KhmerX 客户提供 **Android 原生客户端**：登录、查看贷款、完成 KYC、**查看并确认借款报价**、创建申请、手写签约、提交贷款申请、查看借款进度。

### 1.2 范围内
登录与账号、公司选择与切换、首页、借款记录与详情、KYC 分步填写与材料上传、借款报价与报价确认、手写签名、贷款申请、语言切换、本地缓存与预加载、会话与错误处理。

### 1.3 范围外（本期不做）
- iOS、Flutter Web。
- 运营后台、机构后台、员工端（继续使用 Web）。
- Telegram Mini App 的改动；**Telegram 深链登录**（需新增 Bot webhook，属后端改动）。
- KESS 支付、真实放款与还款（后端未就绪）。
- 推送通知、邀请码解析、生物识别登录。
- 对后端、Web、H5 现有代码的修改，**但 CR-001（无副作用报价）与 CR-002（`assetlinks.json`）除外**，见 `05-flutter-technical-architecture.md` §29。

### 1.3a 统一术语（2026-10-07 冻结，产品与领域文档必须遵守）

| 阶段 | 统一名称（中文 / English） | 含义 | API 兼容名（可保留，不要求为术语改 API） |
|---|---|---|---|
| **Create 前** | **借款报价 / Loan Quote** | 服务端按当前定价计算的、创建申请前展示给用户的费用快照 | 响应体 `Quote`（CR-001）；创建后落在 `loan.billing` |
| **Create 前确认** | **报价确认 / Quote Confirmation** | 用户明确确认该报价并据此创建申请 | `billConfirmed:true`（随 `create`，Option B）；旧动作 `confirm_bill` |
| **贷款生命周期（放款后）** | **还款账单 / Repayment Bill** | 已放款贷款的应还总额、已还、剩余、到期日、还款记录 | 由 `loan.paid`、`loan.billing.total`、`dueAt` 等字段展示 |

规则：
- **Domain 与产品文档不得再混叫 Bill / Quote。** 创建前一律称“借款报价”；放款后的债务数据一律称“还款账单”。
- API 字段 `billing` 映射为领域概念 **Loan Quote**（创建申请时被接受的报价快照）；动作 `confirm_bill` 映射为 **ConfirmLoanQuote**（仅用于 Legacy 流程）。
- `billConfirmedAt` 在新流程里的业务含义：**用户确认创建该 Loan 所依据的 Loan Quote 的时间**。

### 1.4 约束
| 编号 | 约束 |
|---|---|
| C1 | **原则上复用现有后端，不修改 Web/H5/Mini App 现有代码**。App 按 `02-api-contract.md` 调用现有接口；**仅允许解决 Android 主流程阻断问题的最小后端契约增量**：CR-001 无副作用报价（G3 前置）、CR-002 `assetlinks.json`（非阻断）。（2026-10-07 决策调整） |
| C2 | 生产入口为 `api.khmerx.org`（standalone 代理），`PAYEASE_AUTH_MODE=telegram`。 |

| C4 | 一个 App 服务多家公司；**同一时间只激活一家**，可切换；缓存与会话按公司隔离。 |

| C6 | 服务端文案（错误、状态说明、条款）为中文，客户端需自行本地化。 |

## 2. 用户与场景

| 用户 | 场景 |
|---|---|
| 新客户 | 通过公司链接/二维码进入 → 验证手机号 → 设密码 → 完成 KYC → 申请借款 |
| 老客户 | 打开 App 恢复会话 → 查看借款进度 → 会话过期后用密码重新登录 |
| 多公司客户 | 在不同公司之间切换，各自独立登录与数据 |
| 无 Telegram 的用户 | 无法获得验证码；需明确告知原因与替代路径（见 FR-2.9） |

## 3. 功能需求

> 编号用于需求追踪。“验收”均为可测试的结果。

### 模块 1：公司选择与切换
| 编号 | 需求 | 验收 |
|---|---|---|
| FR-1.1 | 首次启动无公司时，显示“选择公司”入口，支持**扫描二维码**与**粘贴公司链接**。链接格式 `https://khmerx.org/app?c=t_<uuid>`。 | 有效链接解析出公司 ID；格式不合法时提示并不发请求 |
| FR-1.2 | App 支持通过 Android App Links 打开 `https://khmerx.org/app?c=…` 直接进入对应公司。 | 链接从浏览器/聊天点开，App 已安装则直达该公司登录页 |
| FR-1.3 | 选定公司后调用 `GET /api/h5/auth`，展示公司名；公司无效/停用（403）时提示并返回选择页。 | 无效 ID 不进入登录流程 |
| FR-1.4 | 本地保存已用过的公司列表（ID、名称、最近使用时间），可在“我的”中切换。 | 切换后会话、缓存、语言开关均为目标公司的 |
| FR-1.5 | 切换公司时，**当前公司的缓存与 Cookie 保留但隔离**，不得串用；退出登录只清除当前公司。 | 公司 A 登录态不会出现在公司 B |
| FR-1.6 | 选公司只是定位，**不代表授权**；未登录前不展示任何客户数据。 | 无会话时除登录页外不可访问业务页面 |

### 模块 2：登录与账号
| 编号 | 需求 | 验收 |
|---|---|---|
| FR-2.1 | 启动时恢复会话：读取该公司的安全存储 Cookie，`GET /api/h5/auth`；`authenticated=true` 直接进首页。 | 杀进程重开仍在登录态（24 小时内） |
| FR-2.2 | 每次进入登录页前先调用 `GET /api/h5/auth` 获取浏览器标识 Cookie 与策略。 | 不出现“登录页面已失效”错误 |
| FR-2.3 | **验证码登录/建号**：输入带国家区号的手机号 → 勾选并展示“同意接收 Telegram 验证码”→ 发送 → 输入 6 位码 → 校验。 | 手机号本地先按 `^\+[1-9]\d{7,14}$` 校验；倒计时与重发间隔 60 秒；码有效 5 分钟 |
| FR-2.4 | 验证码输入支持自动粘贴/聚焦；错误提示区分“码不正确”“已失效需重新获取”“次数用尽”。 | 5 次错误后引导重新获取 |
| FR-2.5 | **密码登录**：手机号 + 密码。失败统一提示，不泄露账号是否存在。 | 成功后进首页 |
| FR-2.6 | 若 `policy.passwordSetup` 为 true 且 `hasPassword` 为 false，登录后**强制进入设置密码页**，完成前不可进入业务页。 | 12–128 位；本地提示强度与长度；成功后继续 |
| FR-2.7 | **找回密码**：验证码重置，两次密码一致；成功后需重新登录。 | 旧会话失效后被送回登录页 |
| FR-2.8 | **退出登录**：调用服务端退出并清空**当前公司**的会话 Cookie 与缓存快照。 | 退出后返回登录页，缓存无残留 |
| FR-2.9 | 无 Telegram 或号码未注册 Telegram 时，给出明确说明与操作（“安装 Telegram”“检查号码”），**不提供短信回退**。 | 不让用户停在无法理解的错误上 |
| FR-2.10 | 会话 24 小时过期或收到 401，保留用户当前页面意图，引导重新登录后回到原位。 | 不丢失未提交草稿 |

### 模块 5：KYC
| 编号 | 需求 | 验收 |
|---|---|---|
| FR-5.1 | KYC 按五个分组分步填写：个人与身份、紧急联系人、工作与资产、收款账户、授权确认。 | 字段与规则见契约 4.5 |
| FR-5.2 | **服务端是可恢复草稿的唯一持久化来源**；当前页尚未保存的编辑只存在**内存**，**磁盘不保存完整 KYC PII**。分组完成（“继续”）时同步保存；切换分组、离开流程、App 进入后台、“Save & Exit”时保存（尽力而为）。（2026-10-07 冻结） | **已成功保存到服务端的分组，杀进程重开后可恢复；当前尚未完成服务器保存的字段可能需要重新输入。** 不承诺杀进程后未保存输入不丢 |
| FR-5.3 | 保存时回传 `revision`；遇到 409 自动重新拉取并保留用户本地编辑，提示“资料已更新”。 | 不静默覆盖他人修改，不丢本地输入 |
| FR-5.4 | 下拉选项的**提交值使用固定字符串**，界面展示按当前语言本地化。内置选项副本并用 `ruleVersion` 校验。 | `ruleVersion` 不一致时提示更新应用 |
| FR-5.5 | 本地先做必填、格式、重复、成对规则校验，错误定位到具体字段。 | 提交前即可发现缺项 |
| FR-5.6 | 材料上传：拍照或选图（PDF 仅限允许的槽位）；上传前**本地限制类型**，自动压缩至 10MB 以内；显示进度，失败可重试（幂等）。 | 自拍/签名/车辆照不能选 PDF |
| FR-5.7 | 条件槽位按 `vehicle`、`housing` 动态显示；车辆材料三选一，提示规则。 | 与契约 4.5 一致 |
| FR-5.8 | 可选“自愿提供设备定位”，需明确授权说明；拒绝不影响提交。 | 定位权限被拒时流程可继续 |
| FR-5.9 | 状态 `submitted` 显示“审核中”并锁定编辑；`needs_info` 显示审核意见（`review.reason`）并允许补件；`approved` 引导申请借款；`rejected` 显示结果。 | 状态与界面一致 |
| FR-5.10 | 已上传材料的缩略图带会话取字节后**仅内存显示，不落盘**。 | 缓存目录中无证件图 |

### 模块 6：借款报价、报价确认、创建申请与签约
| 编号 | 需求 | 验收 |
|---|---|---|
| FR-6.1 | KYC `approved` 且无未结束申请时，可选择**额度（30/50/100/500 USD）与期限（14/28 天）**。 | 参数仅限契约允许值 |
| FR-6.2 | **先报价后创建（2026-10-07 冻结，依赖 CR-001）**：选定金额与期限后，**先获取服务端借款报价（Loan Quote）**，展示本金、费用、到账金额、应还总额、期限；用户**报价确认（Quote Confirmation）**后才创建申请，`create` 携带 `quoteId` 与 `billConfirmed:true`（**Option B**）。**报价不创建申请、不占用名额。** | **创建申请前，用户已看到服务端计算的借款报价**；费用不由客户端计算或估算；新流程**不再单独调用 `confirm_bill`** |
| FR-6.2a | 借款报价过期（TTL 15 分钟）、无效、定价变化（含定价指纹不一致）或参数不一致时，重新获取并**要求用户重新报价确认**。 | 不静默使用新数字 |
| FR-6.2b | **G3 BLOCKED**：CR-001 与 AF-6 修复全部完成并验证前，不得上线任何“先创建后看费用”的流程。 | 解除条件见 §7.1 |
| FR-6.2c | **Legacy 兼容**：同一客户经 Web/Mini App 创建的、处于 `kyc_approved` 且未确认的贷款，App 必须能继续（通过兼容动作 `confirm_bill`，界面称“确认借款报价”）。 | 不因新流程而无法接续旧申请 |
| FR-6.3 | 展示借款条款（`blocks`），**读完后**才可勾选同意；`termsVersion` 取自服务端。 | 未读完不可勾选 |
| FR-6.4 | 手写签名：在画布上签名，导出 PNG 上传；可清除重签；签名为空不可提交。 | 每次签名为新图 |
| FR-6.5 | 签名成功后提交申请（`apply`）。 | 状态变为 `decision_pending` |
| FR-6.6 | 对 409（状态变化、已签、版本变化）给出明确提示并**自动刷新状态**，引导重走所需步骤。 | 不显示为“系统故障” |
| FR-6.7 | 所有写操作使用幂等 `requestId`，同一次操作重试复用同一个；App 被杀后恢复重试仍复用。**`create` 的真正幂等依赖后端 AF-6 修复（P0）**：修复前，同一 `requestId` 重试会得到 409，客户端用 `loan.billing.quoteId === 已确认的 quoteId` 兜底判定“已成功”。 | 不会重复创建申请 |
| FR-6.8 | **Unknown Outcome（结果不确定）**：`create`、`apply`、`sign`、提现/还款等请求超时或断连后，进入“操作状态待确认”，复用同一 `requestId` 并刷新服务端状态，再决定成功/失败/允许重试；**资金类操作不自动重复提交**。 | 不显示假成功，不重复创建 |

## 6. 数据与隐私要点
- 客户端不保存身份证件、证件号、银行账号的明文；表单草稿仅保存在内存与服务端。
- 本地快照仅含贷款状态、金额、时间等展示字段，且按公司与客户隔离。
- 所有网络请求使用 HTTPS，不在 URL 中放个人信息。

## 7. 验收总标准
1. 杀进程重开会话仍有效（24 小时内）。
2. 切换公司后看不到上一家的任何缓存与登录态。
3. 退出后本地缓存与 Cookie 清空，磁盘无证件图与明文 PII。
4. 无会话时业务接口被拒，客户 A 看不到客户 B 的数据。
5. 完成“登录 → KYC 提交 → 审核通过 → 借款报价 → 报价确认并创建申请 → 条款 → 签名 → 提交申请”主流程（创建申请前用户已看到服务端借款报价）。
6. 覆盖 401、403、409、429、503 的行为符合 FR-11。
7. 高棉模式下无非预期中文（条款除外）。
8. 未修改任何现有 Web/H5/后端文件。

### 7.1 Gate 状态与 G3 解除条件
当前：**G0 = FAIL / RECOVERY；G1 = HOLD；G2 = HOLD；G3 = BLOCKED BY CR-001。**（Codex 独立验收 G0 为 FAIL，见 `11`；恢复契约见 `10`。）
G3 解除需**全部**满足，缺一项即保持 BLOCKED：
`CR-001 APPROVED` + `Quote API IMPLEMENTED` + `AF-6 IDEMPOTENCY FIX IMPLEMENTED` + `QUOTE/CREATE ATOMICITY PASS` + `CONTRACT TEST PASS` + `CONCURRENCY TEST PASS` + `UNKNOWN-OUTCOME RETRY TEST PASS` + `ANDROID INTEGRATION TEST PASS`。
