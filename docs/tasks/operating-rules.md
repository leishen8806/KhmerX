# 低沟通运行规则（15 天）

目标：把"来回确认"降到最低。原则：**默认值替代提问、仓库替代聊天、队列替代点名。**

## 1. 任务一次性发完，按队列自取
- Claude 一次性产出全部 15 天的任务卡与 Codex 提示词，放在 `docs/tasks/queue/`：
  - `su-chen.md`：服务端线队列
  - `da-wang.md`：客户端线队列
  - 每张卡包含：编号、依赖、提示词、验收标准、预计耗时。
- 每人做完一张，自己取队列里**下一张依赖已满足**的卡，不需要等晨会点名、不需要问"下一步做什么"。
- 依赖没满足就换下一张可做的；确实全被卡住，在该卡的 PR/Issue 上打 `blocked` 标签并说明被谁卡住（见 §3）。

## 2. 不再为"默认值"提问
- 所有待决事项集中在 `docs/tasks/decision-log.md`，每项已有默认决定，**视为已采用**。
- Codex 提示词里"需求不明确就停下提问"统一改为：**按决策清单的默认继续，并把假设写进 PR 描述的"假设"段**；仅当涉及**安全、数据丢失、花钱、法务、不可逆操作**时才停下提问。
- 技术负责人想改决定：直接改 `decision-log.md` 并注明日期，不需要通知任何人。

## 3. 只有三条沟通渠道
1. **PR 描述与评审评论**：做了什么、假设、风险、回退方法都写在这里。
2. **每天 17:30 前的状态文件** `docs/tasks/status/YYYY-MM-DD.md`（模板见 `orchestration-prompts.md` §8）：完成、未完成、明天计划、阻塞。
3. **`blocked` 标签**：被阻塞时打标签并说明被什么卡住；技术负责人只看带这个标签的项。

除此之外不另外开会、不逐条确认。晨会提示词（A）改为"只在有落后或阻塞时才需要运行"。

## 4. 评审与合并（预先写死）
| 风险 | 例子 | 流程 |
|---|---|---|
| 低 | 文档、测试、脚本、样式 | CI 通过即可合并（技术负责人点合并） |
| 中 | 普通接口、客户端逻辑 | Claude 评审通过 + CI 通过即可合并 |
| 高 | 迁移、鉴权、网关、限流、机构接口、批量脚本 | Claude 评审通过 + CI 通过 + 另一条线同事看过，再合并 |

- 评审触发：把**分支名或 PR 链接**发给 Claude，一行即可，不需要额外说明；Claude 按 `codex-workflow.md` §4 的协议评审，结论只有"通过"或"需修改（附可直接粘贴的修改提示词）"。
- 一次评审只提一轮意见；返修后只复核上轮的"必须修改"项。

## 5. 提问分级（Claude 也遵守）
- Claude 只在这三类事上向技术负责人提问：**不可逆 / 花钱 / 法务**；其余一律采用默认并记录到 `decision-log.md`。
- 技术负责人 24 小时内未回复的提问，按默认值继续。

## 6. 工作目录与提交（避免混在一起）
- 每人独立克隆；每个任务一个 `git worktree`；Codex 会话只绑定自己的 worktree。
- 大旺没有独立 GitHub 账号、在技术负责人的电脑上工作：给他单独一个克隆目录（例如 `KhmerX-dawang`），在该目录里 `git config user.name "大旺"`、`git config user.email "dawang@khmerx.invalid"`；苏晨同理。推送仍用这台电脑的账号，所以提交说明末尾加一行 `Line: client`（或 `Line: server`）来区分是谁写的。
- 小步提交并立即 `git push`，Claude 只能评审已推送的分支。
- 一个分支只放一个任务的改动，禁止 `git add -A` 把别的任务带进来。
