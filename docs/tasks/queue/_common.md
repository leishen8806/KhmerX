# 队列通用前言（每个提示词都隐含包含本页）

1. 先读：`docs/tasks/decision-log.md`、`docs/tasks/codex-workflow.md`、`docs/contracts/ARC-00-error-and-envelope.md`，以及本卡"先读"里列出的文件。不要凭印象写。
2. 不明确的地方：**按决策清单默认继续**，把假设写进 PR 描述的"假设"段。只有涉及安全、数据丢失、花钱、法务、不可逆操作才停下提问。
3. 范围：只改本卡"允许修改"的文件；不整文件格式化；不顺手重构；不引入新依赖（除非本卡写明）；一个分支只放本卡的改动，禁止 `git add -A`。
4. 工作方式：独立 `git worktree`，分支名按本卡；小步提交并立即 `git push`；提交身份用本人名字；PR 小于 400 行，超过就拆成有顺序的多个 PR 并在描述里写顺序。
5. 自查（贴输出摘要到 PR）：`npm test`、`npm run typecheck`、`npm run lint`、`npm run check:client-boundary`（Flutter：`flutter analyze && flutter test`）。
6. 失败响应一律符合 ARC-00；写操作必须考虑幂等与并发；数据库变更必须向前兼容并带回退脚本；不把密钥、令牌、手机号、证件信息写进代码、日志或测试数据；测试数据全部虚构。
7. 交付：PR 描述写"做了什么 / 没做什么 / 假设 / 风险 / 回退方法"；然后把**分支名**发给 Claude 评审。
8. 取卡规则（含堆叠分支）：若依赖卡的 PR 已被 Claude 评审"通过"但技术负责人尚未合并，可以**基于该依赖分支**新建分支继续做（堆叠 PR），并在 PR 描述第一行写明"基于 <依赖分支>，等其合并后需 rebase"；依赖卡仍在"需修改"状态时不得堆叠。其余情况：做完一张，自取队列里**下一张依赖已满足**的卡；全部被依赖卡住时，在该分支或 Issue 上打 `blocked` 标签并写明被谁卡住。
9. 日历（15 个工作日）：第 1 天 10-16（周五）… 第 8 天 10-24（周六，功能冻结）、第 10 天 10-27、第 12 天 10-29、第 13 天 10-30（灰度）、第 15 天 11-02。每张卡的"期限"是目标日，落后超过半天就在状态文件里写明。
