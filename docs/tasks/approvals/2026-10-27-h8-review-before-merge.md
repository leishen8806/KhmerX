## 决定的内容
- 对 **`app/api/**`、`lib/**`、`mobile/**`,以及(2026-10-27 技术负责人补充加入)`deploy/**`、`scripts/**`、`drizzle/**`、`.github/**`** 下的改动,恢复"**先评审后合并**":合并之前,必须有 Claude 的独立评审结论(通过/有条件通过,及其跟进项),且没有未解决的阻塞项。
- 范围:v3 H8 原文的三类路径;随后负责人回复"H8 加入 deploy、scripts、drizzle、.github",四类路径并入。以下"边界"一节中关于这四类路径的说明已按此更新。
- 合并仍由技术负责人(及其指定的人)执行;Claude 不合并、不关闭、不标 Ready。

## 流程(建议的最小做法,负责人可修改)
1. 开发者(大旺、Codex)开 Draft PR,说明改动范围、测试、变异或验证结果;PR 描述写明是否触及上述路径。
2. Claude 评审并给出结论(文档记录或对话回复)。
3. 技术负责人看到"可合并"结论后再合并。没有结论不合并。
4. 触及上述路径但"评审后又有新提交"的,新提交需要重新评审(至少是增量评审)。

## 需要负责人留意的边界
- **不在上述七类路径下的改动不受此规则约束**,例如 `tests/**`、`docs/**`。这意味着只改测试的 PR 不需要等评审,但 Claude 仍建议评审(此前 K-R 系列都是先评审后合并的)。
- **`drizzle/**`(迁移)、`deploy/**`(部署配置)、`scripts/**`(构建与压测脚本)、`.github/**`(CI)已于 2026-10-27 加入范围。** 这些是灰度窗口前后最需要稳定的东西,而且灰度制品和压测工具只认已评审提交 `02ddd0d`。含义:改迁移、部署配置、构建脚本、压测脚本、CI 工作流的 PR,合并前同样需要我的评审结论。
- 本规则不改变已经合入 main 的代码;那批未评审的 PR 仍在清单里(`docs/reviews/kyc-review-wave2-20261024-26.md` §9),需要另外决定是否追认或逐个评审。
- 紧急修复:如果线上或灰度出现严重问题需要立即合并,应由负责人书面指定例外,并在事后补评审。

## 对 v3 的影响
灰度窗口前后的代码基线更稳定,"已评审提交"这个前提不再每天被动摇。代价是每个触及这七类路径的 PR 都要等评审,可能拖慢开发;Claude 会优先评审灰度相关的和体积小的。
