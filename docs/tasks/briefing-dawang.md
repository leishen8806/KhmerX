# 给大旺的配合说明

大旺，项目要在 15 个工作日内（10-16 到 11-02，周日休息，每天 09:00–17:30）让申请主流程扛住 600 人并发。你负责客户端线，代码用 Codex 写，提示词和评审由 Claude 出，技术负责人合并。

## 一、你的任务（按日历）
- 第 1 天（周五 10-16）
  - 上午：R-01 仓库整理。把 `mobile/`、`scripts/dev-app-backend/`、`scripts/apk/`、`docs/flutter-android/` 提交到分支 `app/flutter-import` 并提 PR；补 `.gitignore`，不要提交构建产物。
  - 其余时间：B0 基线压测脚本（k6）和 D1 `apiFetch` 升级。提示词在 `docs/tasks/codex-prompts/day1.md`，整段粘给你的 Codex。
- 第 2 天（周六）：跑 B0，出 50 / 100 / 300 人的压测报告，17:00 前交给 Claude 过闸门 A。
- 第 3–7 天：上传压缩与断点重试（Web 和 Flutter）、关键错误按错误码显示多语言（去掉按中文文案判断的逻辑）、管理后台适配员工列表分页、Flutter 对齐新错误体。每天的具体任务和提示词由 Claude 在 09:00 晨会里发你。
- 第 8 天（周六 10-24）：功能冻结，之后只改缺陷。
- 第 9–12 天：配合压测，修压测暴露的客户端问题，扩展压测脚本。
- 第 13–15 天：灰度期间收集反馈和错误，配合回退。

## 二、你和苏晨怎么配合
1. 错误码是接口约定：错误体和错误码以 `docs/contracts/ARC-00-error-and-envelope.md` 为准。苏晨做 S2（服务端按契约改），你做 D1 和错误码显示（客户端按契约用）。S2 合并之前，用契约里的格式做测试数据；合并后再联调。
2. 目录归属：你改 `app/` 页面、`components/`、`lib/api-client.ts`、`mobile/`；`lib/store.ts`、`lib/domain.ts`、`app/api/`、`lib/` 其余部分是苏晨的，不要动。新增多语言文案放进你自己新建的文件，不要改 `lib/i18n.tsx` 这个巨型单行文件。
3. 接口变更先对齐：员工列表分页、状态接口的响应形状等，由 Claude 在契约里先写清，你们两人确认后再各自实现；不要靠猜。
4. 互相看 PR：你的 PR 合并前，涉及客户端协议的部分请苏晨过一眼；苏晨的接口变更 PR，请你看一下客户端是否受影响。
5. 有阻塞就喊：被对方的合并卡住，在看板上打 `blocked` 标签，并在次日晨会前告诉技术负责人，不要等。

## 三、每天的节奏
- 09:00–09:30：晨会，拿当天任务和提示词（最多 3 个）。
- 09:30–16:00：用 Codex 开发，每个任务一个独立的 `git worktree` 和分支 `feat/client/<编号>`，PR 控制在 400 行以内。
- 提交 PR 前跑：`npm test`、`npm run typecheck`、`npm run lint`、`npm run check:client-boundary`；Flutter 跑 `flutter analyze` 和 `flutter test`。
- 16:00–17:00：技术负责人集中合并，你的 PR 要在这之前经过 Claude 评审。
- 17:00–17:30：写当天状态文件 `docs/tasks/status/日期.md`（完成了什么、没完成原因、明天计划、阻塞）。

## 四、几条铁律
- 只改任务提示词里"允许修改"的文件；不整文件格式化；不顺手重构。
- 遇到需求不明确或要越出范围，让 Codex 停下来问，不要让它猜。
- 压测只能对本地或预发环境跑，不得对生产域名运行。
- 测试数据全部虚构，不要用真实手机号和证件。
- 评审通过之前不要催合并；高风险的 PR（鉴权、数据迁移）要等预发演练。

## 五、第一天要先确认的两件事
1. 你本机能不能把本地后端跑起来（B0 压测需要）；`scripts/dev-app-backend/` 是按旧版后端写的，官方 `main` 之后改过，可能要调整，跑不通就第一时间告诉 Claude，不要自己花半天硬调。
2. 把你的 GitHub 用户名告诉技术负责人，用来填 CODEOWNERS。
