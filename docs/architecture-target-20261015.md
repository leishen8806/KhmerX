# KhmerX 目标架构（仅架构层，不含业务细节）

日期：2026-10-15　状态：草案，待运行环境（A/B）确认

## 1. 原则
1. 客户端只做展示和采集，不直接访问数据库、对象存储或第三方；所有业务规则只在服务端。
2. 业务服务端无状态，可水平扩展；状态只放在数据库、对象存储、队列。
3. 金融服务公司系统与持牌机构系统是两个独立系统：独立部署、独立数据库、独立员工账号，只通过签名接口通信。
4. 对外接口只有一套契约，Web、App、小程序、管理后台共用同一套规则；契约写成可测试的文件。
5. 所有跨系统调用都异步可重试、幂等、可对账。

## 2. 组件与职责
| 组件 | 属于 | 职责 |
|---|---|---|
| H5 / 小程序 | 客户端 | 同一套网页，客户入口 |
| App（Flutter） | 客户端 | 客户入口，按浏览器兼容方式访问同一接口 |
| 管理后台 | 客户端 | 员工入口（金融服务公司员工） |
| 负载均衡 / 网关 | 边缘 | TLS、路由、限流、真实客户端 IP、安全头；不承载业务授权 |
| 业务服务端 | 金融服务公司 | 三类入口共用一套业务规则：客户入口、员工入口、系统入口 |
| 机构对接层 | 金融服务公司 | 发件箱出站、回调入口、重试、对账 |
| 数据库 | 金融服务公司 | 按行存储业务数据，只被业务服务端访问 |
| 对象存储 | 金融服务公司 | 上传的文件，短期凭证访问 |
| 队列 | 金融服务公司 | 验证码、通知、文件扫描、机构投递、定时任务 |
| 机构服务端 | 持牌机构 | 受理申请、回调通知 |
| 审批工作台 | 持牌机构 | 机构员工使用 |
| 独立数据库 | 持牌机构 | 机构自己的数据，不与金融服务公司共用 |

## 3. 通信规则
- 客户端 → 网关 → 业务服务端：HTTPS。浏览器类用同源 Cookie（SameSite=Strict + Origin 校验）；App 沿用 Cookie + Origin，不新增 Bearer（现阶段冻结决策）。
- 业务服务端 → 机构服务端：签名（HMAC + 时间戳 + nonce + 幂等键），出口地址白名单，通过发件箱异步发送。
- 机构服务端 → 业务服务端：签名回调，防重放，幂等，已实现。
- 业务服务端 → 数据库 / 对象存储 / 队列：只在内网。
- 第三方（Telegram、地址解析、文件扫描）只由服务端调用，凭据只在服务端。

## 4. 部署拓扑
```
客户端 ──HTTPS──▶ 负载均衡/网关 ──▶ 业务服务端 (≥2 实例)
                                     ├─▶ 数据库（主 + 备）
                                     ├─▶ 对象存储
                                     └─▶ 队列 / 定时任务
                                     │
                       签名 HTTPS ◀──┴──▶ 持牌机构系统（独立部署）
                                           ├─ 机构服务端 (≥2 实例)
                                           ├─ 审批工作台
                                           └─ 独立数据库（主 + 备）
```
- 环境：开发、预发（与生产同构，机构侧用模拟或预发机构）、生产。三个环境的数据、密钥、域名互相隔离。
- 运行环境：**已选 B**：Node 服务 + PostgreSQL + 对象存储 + 负载均衡（需要把 SQLite 方言迁到 Postgres）。现有一台 VPS 用于金融服务公司系统，另增一台 VPS 用于持牌机构系统。
- 现状的"单台 VPS + Miniflare"仅作测试环境，不作生产。

## 5. 数据层原则
- 业务数据按行存储，每个客户的数据独立成行，用行版本做并发控制；禁止"整个租户一块 JSON"。
- 客户端接口只读本人数据；员工列表走分页和索引。
- 迁移：双写 → 回填 → 切读，保留回退开关。
- 备份：自动备份加定期恢复演练；对象存储带版本。

## 5.1 数据库与备份（环境 B）
- 备份必须放在**生产服务器之外**，不一定要单独一台"数据库服务器"：用异地的 S3 兼容对象存储即可（便宜、可版本化、可锁定不可改），两个系统各用独立的桶、独立的账号和密钥（金融服务公司被攻破时，机构备份仍安全）。
- 备份方式：PostgreSQL 每周全量 + 每日增量 + 持续归档 WAL（pgBackRest 或 WAL-G），可恢复到任意时间点；备份在客户端加密，密钥另存；对象存储文件跨区域复制。
- 目标：RPO ≤ 5 分钟；RTO 第一阶段 ≤ 2 小时，第二阶段 ≤ 30 分钟。每月自动恢复演练（恢复到临时机器并跑校验查询）。
- 部署分两阶段：
  - 阶段 1（灰度，约 150 人以内）：两台 VPS 各自"应用 + PostgreSQL"同机，数据库走 WAL 归档到异地对象存储；单机故障需要从备份恢复。
  - 阶段 2（600+ 并发）：金融服务公司系统把数据库拆到独立服务器：≥2 台应用 + 1 台数据库主库 + 1 台只读/热备副本（内网互通，无公网 IP，防火墙只放行应用服务器）；数据库前加连接池（pgbouncer）。持牌机构系统流量小，可维持应用与数据库同机，但必须有异地备份和副本或可快速恢复的备机。
- 也可以在阶段 2 直接使用供应商的托管 PostgreSQL（自动备份、时间点恢复、副本），以减少自己运维数据库的负担。
- 持牌机构的数据库、备份、密钥与金融服务公司完全分开，不共用账号和存储。

## 5.2 落地：DigitalOcean 新加坡（SGP1）
| 需要 | DigitalOcean 产品 | 说明 |
|---|---|---|
| 应用服务器 | Droplet（建议 ≥2 台，同一 VPC） | 金融服务公司系统；持牌机构系统单独一个团队/账号 |
| 入口 | Load Balancer + Reserved IP | TLS 在入口终止；用 `X-Forwarded-For` 传真实客户端 IP，供限流使用 |
| 数据库 | Managed PostgreSQL（主 + 备用节点，内置连接池） | 两个系统各一个独立集群，只允许同 VPC 的应用访问 |
| 文件 | Spaces（S3 兼容） | 直传 + 短期预签名链接；文件加密 |
| 队列 | 先用 PostgreSQL 任务表或 Redis（Managed） | 量大再换专用队列 |
| 网络 | VPC + Cloud Firewall | 数据库无公网访问；两系统之间只放行签名 HTTPS 的出口地址 |
| 监控 | DO Monitoring + 外部拨测 + 日志集中 | 告警分级 |
- 备份：Managed PostgreSQL 自带每日备份和时间点恢复，但在同一供应商、同一区域，**不等于异地备份**。另需每日逻辑备份（加密）到**另一区域/另一账号（或另一供应商）**的对象存储，并做恢复演练。
- 两个系统隔离：独立团队/账号、独立 VPC、独立数据库集群、独立 Spaces 桶、独立密钥。
- 数据所在地：数据在新加坡机房，客户资料和人脸数据是否允许存放境外，需法务确认。

## 5.3 读写分离与 Redis
- 数据库：**逻辑上区分、物理上先不拆**。代码里写库、读库用两个连接配置（`DB_WRITE_URL` / `DB_READ_URL`），初期两者指向同一个主库；客户端面向的读取（贷款状态、资料）永远走主库，避免写后读到旧数据。
- 备用节点只用于故障切换，不用于读。只读副本只在员工报表、导出、对账这类重查询出现压力时才加，且这些页面接受秒级延迟。
- Redis：只做可丢失的辅助数据：限流计数、一次性校验（initData 重放、验证码尝试次数）、短期缓存；**不作为数据来源**。会话、业务数据、机构发件箱都在 PostgreSQL。Redis 只用主节点，不读副本；Redis 不可用时：读类接口放行限流，验证码发送和登录类接口按"宁可拒绝"处理。
- 队列：初期用 PostgreSQL 任务表（`SKIP LOCKED`，如 Graphile Worker / pg-boss），机构发件箱必须和业务数据在同一事务；暂不引入 Redis 队列。

## 6. 可靠性与扩展
- 业务服务端无状态，实例数随负载增减；会话存数据库，不存内存。
- 限流按用户和可信客户端 IP 分别计数，原子计数。
- 上传：客户端直传对象存储，异步扫描，状态为"待扫描 / 可用 / 被拒绝"。
- 队列任务：重试、退避、死信；外部不可用时熔断并降级提示。
- 发布：蓝绿或滚动，功能开关，只读维护模式。

## 7. 安全边界
- 机构系统与金融服务公司系统不共用数据库、会话、文件存储、密钥；网络只放行必要的通路。
- 密钥放密钥管理，不进代码、不进前端；生产启动时断言测试模式关闭。
- 统一错误体 `{ code, error, requestId }`，不返回内部异常；所有写操作带 `requestId`，审计只增不改。

## 8. 可观测与运维
- 结构化日志带 `requestId`；指标：p95 延迟、错误率、数据库耗时、队列积压、机构投递成功率；告警分级。
- 压测：上线前 600 人并发、1000 人压力、2 小时持续测试。
