# PayEase 编号与订单号规则方案

## 1. 目标与边界

- 对外展示编号统一为 10–16 位，本方案固定为 16 位，便于人工识别、复制和客服查询。
- 编号可识别业务对象和来源渠道，但不编码公司、手机号、证件号、金额或状态，避免泄露敏感信息和形成可枚举规则。
- 现有 UUID、SHA-256 摘要和数据库主键全部保留，继续承担外键、签名绑定、文件对象和审计关联职责。
- 公共编号只由服务端生成，客户端不得提交自定义编号；唯一性由数据库约束和生成重试共同保证。

## 2. 编号格式

```text
实体 1 位 + 渠道 2 位 + 日期 6 位 + 随机 7 位
```

示例：`OTG2610097K3M8Q2`

| 位置 | 长度 | 含义 | 说明 |
|---|---:|---|---|
| 第 1 位 | 1 | 实体类型 | 只使用大写字母 |
| 第 2–3 位 | 2 | 来源渠道 | 固定渠道码，不用于权限判断 |
| 第 4–9 位 | 6 | 创建日期 | `YYMMDD`，按柬埔寨 `Asia/Phnom_Penh` |
| 第 10–16 位 | 7 | 随机段 | Crockford Base32 大写字符，排除 `I/L/O/U` |

实际校验格式：

```text
^[A-Z][0-9A-HJ-KM-NP-TV-Z]{2}[0-9]{6}[0-9A-HJ-KM-NP-TV-Z]{7}$
```

日期只用于人工定位，不作为排序或唯一性的依据；正式排序仍使用 `created_at`。

## 3. 实体代码

| 实体 | 代码 | 示例 | 使用范围 |
|---|---|---|---|
| 客户 | `C` | `CTG261009...` | 客户中心、客户 360、导出 |
| 贷款订单 | `O` | `OTG261009...` | 借款记录、贷款申请、放款、还款 |
| KYC 资料 | `K` | `KTG261009...` | KYC 队列、审核、补件、复核 |
| 文件材料 | `F` | `FTG261009...` | 文件列表、审计引用；不直接作为下载 URL |
| 账单/报价 | `B` | `BTG261009...` | 账单、费用确认、合同快照 |
| 工单 | `T` | `TTG261009...` | 客服、投诉、争议 |
| 审计记录 | `A` | `ATG261009...` | 审计查询和导出 |

内部请求编号、会话令牌、签名哈希、Webhook 幂等键和第三方 `event_id` 不转换为业务编号，继续使用现有随机值或外部值，并禁止在普通业务页面展示。

## 4. 渠道代码

| 渠道 | 代码 | 记录要求 |
|---|---|---|
| Telegram Mini App | `TG` | 同时保存 `source_bot_id` |
| H5 | `H5` | 保存入口域名和客户端版本 |
| 原生 APP | `AP` | 保存 APP 版本和设备渠道 |
| 管理后台创建 | `AD` | 保存操作者员工 ID 和岗位 |
| 持牌机构/API 回调 | `IN` | 保存机构 ID、外部事件 ID 和幂等键 |
| 系统任务/历史补录 | `SY` | 保存任务名或补录原因 |

渠道码用于查询和展示，不能替代租户、岗位或数据范围校验。所有查询仍必须先按公司、部门、机构权限过滤。

## 5. 数据字段建议

### 5.1 客户

新增：`customer_ref`、`source_channel`、`source_bot_id`、`created_at`。

客户内部 `customer_id` 保持现状，不再直接返回到普通客户端或 CRM 表格。

### 5.2 贷款订单

新增：`order_ref`、`source_channel`、`source_bot_id`、`created_at`。

`Loan.id` 继续作为内部主键，`order_ref` 作为唯一对外订单号。订单关联的客户、KYC、账单、签约、流水仍使用内部主键。

### 5.3 KYC、文件、账单、工单、审计

各自增加对应的公共编号字段：`kyc_ref`、`file_ref`、`bill_ref`、`ticket_ref`、`audit_ref`。文件对象 key 和加密上下文继续使用内部文件 ID，不把公共编号直接当作存储路径。

## 6. 唯一性与生成算法

1. 服务端按实体、渠道和柬埔寨日期生成编号。
2. 随机段使用密码学安全随机源，不能使用递增序号、时间戳截断或客户端随机数。
3. 建议增加统一表 `public_identifiers`：

   ```text
   ref PRIMARY KEY
   entity_type
   internal_id
   tenant_id
   source_channel
   created_at
   ```

   同时在各业务表保留实体字段唯一索引，形成双重保护。
4. 生成和写入必须在同一事务中完成；发生唯一冲突最多重试 5 次，仍失败则返回系统错误并记录告警。
5. 编号生成后永久不变；订单状态、公司切换、渠道配置变化都不能重新生成。

## 7. 现有代码风险与处理

当前发现的主要问题：

- 贷款页面和 CRM 列表直接展示 `Loan.id` UUID，例如截图中的长 UUID。
- 客户页面直接展示 64 位 `customerId` 摘要，人工不可读且暴露内部身份绑定形式。
- KYC 资料 ID 当前由摘要生成，文件、审计、工单等多处直接使用 UUID。
- `quoteId` 使用 UUID，适合作为账单版本绑定，不适合作为客户可见编号。
- 订单、客户、KYC 没有统一的 `source_channel` 字段，当前只能间接从 bot 或登录模式推断。

处理原则：不修改已有内部 ID，不做字符串截断冒充新编号，不把 UUID 的前 8 位作为正式编号。

## 8. 分阶段实施

### 阶段一：字段与生成器

- 增加编号生成器、格式校验、渠道枚举和唯一性测试。
- 新增公共编号字段及 `public_identifiers` 表。
- 新建数据只写入内部 ID、公共编号和来源字段。

### 阶段二：历史数据回填

- 按原始创建时间回填公共编号。
- 能确定的订单从 `bot_id` 和认证模式推断 `TG/H5`；无法确定的历史数据统一标记 `SY`，并写入回填批次。
- 任何重复或异常记录进入人工复核清单，不覆盖原始主键。

### 阶段三：接口与页面切换

- CRM 列表、客户 360、KYC 队列、账单、Telegram 通知和 CSV 导出改用公共编号。
- API 返回 `customerRef/orderRef/kycRef`；内部 `id` 仅供服务端关联或受控审计使用。
- 查询支持公共编号精确匹配，不支持通过部分 UUID 枚举数据。

### 阶段四：兼容与收口

- 旧内部 ID 仅保留在内部签名接口的兼容映射中，并设置迁移期限。
- 生产日志、普通导出、客服截图和客户端响应不再输出原始 UUID 或 64 位客户摘要。
- 完成租户隔离、岗位权限、导出脱敏和第三方回调回归测试后，再移除普通 API 的内部 ID 字段。

## 9. 验收标准

- 所有新建客户、订单、KYC、文件、账单、工单和审计记录均有 16 位公共编号。
- 同一公司、跨公司、跨实体、跨渠道均无重复公共编号。
- 生成 100,000 个编号无重复；碰撞重试和事务回滚有测试覆盖。
- Telegram、H5、APP、后台、机构回调五类来源可准确识别。
- CRM 页面和导出不再显示截图中的 UUID 和 64 位 `customerId`。
- 使用公共编号查询时仍执行公司、部门、岗位和机构范围校验。
- 旧贷款、旧 KYC、旧文件、旧审计关联和签约哈希全部保持可回读。
- 回归验证申请 → KYC → 账单 → 签约 → 审批 → 放款 → 还款全链路，以及回调幂等、文件访问和审计导出。

本方案只定义编号规则和迁移边界，未直接修改现有业务数据；通过评审后再进入数据库迁移和接口切换阶段。
