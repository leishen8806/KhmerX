# KhmerX / PayEase 业务后台管理产品需求方案

版本：v1.1（CRM 菜单与应急机制复核版）  
复核日期：2026-10-05  
适用范围：金融服务机构业务后台、持牌机构后台、运营与客服工作台  
配套客户端：Telegram Mini App、H5 及官网  
状态：产品基线，开发、测试和上线评审依据

> 本文按产品运营、业务作业、机构审批、审计安全和平台配置五个责任域组织；后台菜单进一步采用 CRM 的对象中心结构。本文中的“已实现”以当前代码为准；“上线前补齐”不等于当前已经具备。

## 1. 产品定位与目标

KhmerX 后台是面向全部社会用户的 Cambodia-native Lending OS 业务控制台：金融服务机构负责客户、KYC、产品和运营流程；持牌机构通过受控 API 接收申请、审批并返回结果；后台保存可追溯的业务、账务、通知和操作证据。

### 1.1 设计目标

1. 一笔申请从注册、KYC、审核、审批、签约、放款、账单、还款到结清可追踪。
2. 产品规则可配置，但每次生效都必须有版本、审批人和生效时间。
3. 员工只看到其公司、部门、机构或分单范围内的数据。
4. 高风险动作实行发起人与复核人分离，禁止自审、自放款、自复核。
5. 所有资料修改、权限变化、资金动作和登录活动均可审计。
6. 支持中文、English、高棉语；后台保留三语切换，客户端语言由用户选择。

### 1.2 当前系统边界

当前项目仍是测试资金闭环和交互原型：KYC 使用合成资料，放款、提现、还款、通知为模拟执行，资金不是银行真实资金；真实支付、真实银行、真实短信和公开客户站点不应在未完成合规和安全评审前启用。

## 2. 系统与域名拓扑

| 系统 | 域名/入口 | 主要用户 | 责任边界 |
|---|---|---|---|
| 官网 | `khmerx.org` | 社会用户、合作方 | 品牌、产品说明、新闻、帮助和客服入口，不承载后台业务写操作 |
| Mini App / H5 | `payease.khmerx.org` | 客户 | 注册、KYC、申请、签约、钱包、账单、还款和通知 |
| 业务后台 | `admin.khmerx.org` | 金融服务机构员工 | 客户/KYC、产品、审批协同、贷后、客服、运营和审计 |
| API 独立系统后台 | `api.khmerx.org`（API 服务）及独立控制台入口 | 三端、持牌机构和技术管理员 | API 产品、应用凭据、版本、回调、限流、调用日志和审计；不直接暴露数据库 |
| 持牌机构后台 | 持牌机构独立服务器/独立网络入口 | 持牌机构审批员 | 只处理分配给本机构的审批、复核和受控放款动作 |

反向代理由 Caddy/Nginx 统一处理 HTTPS、域名路由、请求体大小、基础安全头和上游服务隔离。任何前端页面不得绕过 API 直接访问数据库或外部支付服务。持牌机构服务器不得与金融服务机构后台共用数据库、员工会话或文件存储；双方仅通过签名 API 和白名单网络通信。

API 独立系统后台需要具备独立登录、应用/机构管理、API Key 或 OAuth 客户端管理、接口版本、回调地址、IP 白名单、限流策略、请求/响应摘要、失败重试和调用审计。正式开放前必须完成开发者/机构授权、密钥轮换、沙箱与生产环境隔离及回调验签。

## 3. 组织、部门与责任模型

### 3.1 组织层级

```text
平台
└── 金融服务机构（Company / Tenant）
    ├── 产品运营部门
    ├── KYC 审核部门
    ├── 贷后/催收部门
    ├── 财务/放款部门
    └── 关联持牌机构（独立机构范围）
```

没有工厂或企业审核环节。企业/工厂信息如未来需要，只作为选填资料或单独产品线，不得成为全部社会用户申请的前置条件。

### 3.2 部门与机构管理需求

| 功能 | 需求 |
|---|---|
| 公司 | 公司名称、入口代码、状态、默认语言、时区、数据隔离标识 |
| 部门 | 部门名称、类型、负责人、成员、启用状态；支持产品运营、KYC、贷后、财务等类型 |
| 持牌机构 | 机构名称、许可证/备案信息、API 状态、回调地址、可处理产品和区域 |
| 分单 | 客户、KYC、审批、放款、还款、贷后任务分别记录承接部门/机构及版本 |
| 默认规则 | 可设置自动分单；只影响新记录或尚无承接信息的历史记录，不覆盖已分配记录 |
| 成员 | 邮箱、姓名、语言、角色、部门、机构范围、启用状态、权限版本 |
| 交接 | 负责人离职/停用时，任务必须转交或进入待分配队列，并产生审计事件 |

### 3.3 产品运营部门职责

产品运营部门不直接修改客户身份证号、资金流水或持牌机构审批结果；其职责包括：

- 产品和费率草案维护、上线申请和版本生效管理；
- 客户队列、补件、通知模板、活动/公告和服务规则管理；
- KYC/审批/贷后队列分配和 SLA 监控；
- 运营数据、漏斗、逾期和客服指标查看；
- 对异常记录发起复核或工单，不通过绕权方式改写核心数据。

## 4. 角色、权限与数据范围

### 4.1 角色定义

| 角色 | 主要职责 | 默认数据范围 | 可执行高风险动作 |
|---|---|---|---|
| 公司管理员 `admin` | 公司、成员、部门、系统配置和例外处理 | 本公司全部数据 | 受约束的管理放款/还款、权限和配置；不能跳过 KYC/审批校验 |
| 审计员 `audit` | 查看审计、登录、修改和异常记录 | 被授权的全公司只读 | 不得修改业务数据 |
| 产品运营 `ops` | 运营队列、分单、通知和产品运营 | 本部门/分单范围 | 发起规则或分单变更，不直接完成复核 |
| KYC 审核主管 `dept_admin` | KYC 部门成员和待办管理 | 本部门 | KYC 分单、改派、队列处理；受限字段修改需专门权限 |
| KYC 审核员 `kyc` | KYC 审核、退回补件、结果记录 | 本部门及被分配客户 | 审核/退回，不得自行修改后直接通过 |
| 贷后主管 `collection_admin` | 贷后策略、任务、改派和催收监督 | 本公司贷后范围 | 关闭/改派任务需留痕 |
| 贷后客服 `collector` | 跟进客户、记录沟通、催收提醒 | 分配给本人任务 | 不得改写贷款本金、费率或审批结果 |
| 机构审批员 `lender` | 持牌机构审批 | 本机构分配申请 | 通过/拒绝，需进入复核链 |
| 机构复核员 `checker` | 审批结果复核 | 本机构分配申请 | 独立复核，不得与发起人相同 |
| 放款员 `finance` | 发起放款 | 指定放款机构范围 | 发起放款，不得独立完成最终确认 |
| 放款复核员 `finance_checker` | 放款复核 | 指定放款机构范围 | 独立确认放款 |

### 4.2 权限原则

1. **RBAC + 数据范围**：角色决定动作，部门/机构/分单决定可见数据。
2. **最小权限**：新成员默认无业务写权限，必须由管理员明确分配。
3. **字段级权限**：KYC 资料、证件号码、联系方式、收入资料、银行信息、签名和资金字段分开授权。
4. **Maker-Checker**：审批、放款、关键 KYC 修改和资金冲正不得由同一员工完成发起和复核。
5. **版本失效**：停用员工、修改角色/部门/机构范围或重置密码时，旧会话立即失效。
6. **拒绝越权**：服务端每次动作重新检查公司、成员版本、分单版本、订单状态和权限；前端隐藏按钮不算权限控制。

### 4.3 权限矩阵（摘要）

| 模块 | 查看 | 新建/发起 | 审核/确认 | 修改 | 导出 |
|---|---|---|---|---|---|
| 客户与 KYC | 运营/KYC/审计按范围 | 客户端提交 | KYC 审核员 | 独立 KYC 修改权限 | 脱敏且需授权 |
| 产品与费率 | 运营/管理员 | 运营草拟 | 管理员/指定复核 | 版本化修改 | 管理员 |
| 贷款申请 | 运营/机构按范围 | 客户端提交 | 机构审批/复核 | 仅状态允许的补件字段 | 审计/授权运营 |
| 放款 | 财务按机构 | 放款员 | 放款复核员 | 禁止直接改账 | 审计/财务主管 |
| 还款与账单 | 贷后/财务 | 财务登记/渠道回调 | 复核或管理员 | 通过冲正流程 | 财务/审计 |
| 贷后任务 | 贷后 | 主管/系统 | 主管关闭 | 改派有记录 | 主管/审计 |
| 员工与权限 | 管理员/审计只读 | 管理员 | 管理员 | 管理员，变更审计 | 管理员 |
| 审计与安全 | 审计/管理员 | 系统写入 | 不允许删除 | 不允许覆盖 | 审计导出 |

## 5. 后台产品模块需求

### 5.1 工作台与待办

- 按待审核 KYC、补件、待审批、待放款复核、逾期、客服工单和系统异常展示队列；
- 每条待办显示申请编号、客户脱敏信息、金额、状态、SLA、承接部门/机构和最后操作人；
- 支持关键词搜索：用户 ID、用户名称、身份证号掩码/末四位、手机号掩码、申请编号、Loan ID；
- 筛选按状态、日期、部门、机构、产品、风险等级、逾期天数；
- 搜索结果仍受当前员工数据范围限制，不能用精确身份证号绕过权限。

### 5.2 客户与 KYC

- 查看客户基础信息、KYC 版本、提交时间、当前状态、补件原因和审核历史；
- KYC 分为基础身份、联系人、地址/定位、收入证明、工作/资产、银行信息、手写签名及附件；
- 紧急联系人至少两种关系，第三个联系人选填；同名同电话不得重复；后端入库前再次校验关系唯一性和数据合法性；
- 客服可修改 KYC 仅限被授予的字段权限；证件号码单数字纠错也必须生成前后值审计并进入复核；
- 附件支持图片/PDF，目标上限 10MB；当前代码/部署基线若为 5MB，必须在产品验收前统一前后端、代理和扫描器限制；
- 上传必须做扩展名、MIME、文件头、大小、病毒扫描、路径穿越、重复上传和存储隔离检查；ClamAV 或云扫描异常时默认拒绝入库；
- 图片保存原始清晰版本，预览使用受控缩略图，后台查看必须防止原文件 URL 外泄；
- 银行手机号、Telegram 授权、注册定位、签名等敏感信息需要独立同意记录和访问日志。

### 5.3 产品、价格与费用

- 产品名称、金额上下限、期限、利息、服务费、罚息、还款方式、币种和适用地区；
- 费率规则必须有 `draft → review → active → retired` 生命周期；已生成合同、账单和贷款不得被新费率重算；
- 申请确认页展示本金、手续费、实际到账、应还总额、各期明细、到期日和逾期后果；
- 任何费率调整必须记录旧值、新值、变更原因、操作者、复核人和生效时间。

### 5.4 贷款申请与决策

- 贷款状态以当前服务端状态机为准：`registered`、`kyc_pending`、`needs_info`、`kyc_approved`、`decision_pending`、`approved`、`rejected`、`signed`、`active`、`closed`；KYC 审核状态单独使用 `draft`、`submitted`、`needs_info`、`approved`、`rejected`，不得混用两套状态；
- 自动规则只输出建议和风险原因，人工复核可以通过/拒绝/退回补件，但不能删除原始决策依据；
- 记录规则版本、输入快照、结果、命中规则、人工意见和最终决策人；
- 任何状态跳转需由服务端状态机校验，不接受客户端直接传目标状态。

### 5.5 放款、账单、还款与对账

- 审批通过后生成 Loan ID、本金、利息、费用、放款日、到期日和账单计划；
- 放款必须经过合同签署、费用确认和放款复核；
- 账单保存每期本金、利息、服务费、罚息、应还日、已还额、剩余本金和 Total Due；
- 还款分配顺序默认：罚息 → 利息 → 费用 → 本金，规则变更必须版本化；
- 每笔资金动作使用唯一流水号和幂等键，重复请求不得重复入账；
- 当前为测试资金；接入真实渠道前必须新增支付适配层、回调验签、对账、冲正、退款和资金隔离设计。

#### 公司级放款限额与资金监管配置

公司管理员可配置并发布以下公司级资金控制参数；参数变更必须经过复核并写入审计，按公司/租户隔离：

| 配置项 | 当前配置 | 计算口径 | 触发动作 |
|---|---:|---|---|
| 每日放款限额 | 10,000 USD | 按公司时区自然日累计“放款成功”金额；仅成功入账计入，失败、取消和重复幂等请求不计入 | 达到限额后停止新的放款确认，进入待处理队列并通知管理员/财务 |
| 每月放款限额 | 30,000 USD | 按公司时区自然月累计“放款成功”金额；跨月不回溯重算历史记录 | 达到限额后停止新的放款确认，直至下一个自然月或经授权调整限额 |
| 资金监管预警线 | 20% | 可用监管资金余额 ÷ 已配置监管资金池/额度；小于或等于 20% 时触发 | 发送后台、Bot 和审计告警；默认不自动改变历史贷款，是否阻断新放款由公司风控策略单独配置 |

补充规则：

- 每日限额在公司时区 00:00 重置，每月限额在公司时区每月 1 日 00:00 重置；时区变更不得改写历史累计值；
- 限额检查必须在服务端、同一资金事务内完成，使用整数最小货币单位和幂等键，防止并发放款突破限额；
- 放款限额命中、资金监管预警、限额调整、人工解除和告警确认均需记录操作者、前后值、原因、时间、请求 ID 和关联流水；
- 限额配置至少需要 `daily_disbursement_limit`、`monthly_disbursement_limit`、`regulatory_warning_ratio`、`timezone`、`version` 和 `effective_at` 字段；
- 当前代码仍为测试资金闭环，以上配置先作为产品基线；接入真实资金前必须完成数据库迁移、并发测试、对账验证、持牌机构确认和上线审批。

资金监管告警属于风控事件，不是普通运营提示。触发后自动建立风险事件，关联公司、资金池、累计放款、监管余额和关联流水；在风险事件关闭前，管理员和财务复核员可查看，但普通运营人员不得解除或覆盖。

### 5.6 贷后与客服

- 到期前提醒、逾期提醒、催收任务、补件提醒和客户投诉统一进入任务/工单；
- 按最终逾期天数计算规则，第三天开始计数；超过 15 天进入黑名单后停止继续计数；规则结果保存快照，不依赖实时重算；
- 贷后客服只能记录联系结果、承诺还款、补件和沟通证据，不能修改本金、费率或历史流水；
- 客服入口、Telegram Bot 通知和三语模板由后台统一维护，发送失败需要可重试和失败原因。

### 5.7 员工、权限与机构配置

- 管理员创建员工、分配角色/部门/机构、启用/停用、重置密码和查看会话；
- 独立员工密码只显示/下载一次，数据库只存 PBKDF2-SHA256 摘要；重置需填写原因，旧会话和密码版本立即失效；
- 禁止管理员通过修改前端请求体获得其他公司数据；所有权限由 API 重新判定；
- 持牌机构 API 凭据只存服务端 secret，后台仅显示掩码和连接状态。

### 5.8 通知与内容运营

- 通知模板支持中文、English、高棉语；按用户语言选择模板，缺失时按明确的默认语言回退；
- 已知通知：注册未完成、KYC 结果、放款、还款提醒、催款提醒、补件和投诉进度；
- 公司新闻、行业资讯、帮助内容由管理后台统一发布，保留草稿、审核、发布时间、作者和下线记录；
- Bot 多渠道支持独立启用、连接检查、故障切换和消息幂等；不因单一 Bot 风控导致客户身份记录丢失。

### 5.9 数据分析与报表

- 统计注册、KYC 提交/通过、申请、审批、放款、还款、逾期、补件、通知发送和客服解决率；
- 一方事件记录使用统一事件名、locale、screen、properties 和时间戳；properties 禁止保存原始身份证号、手机号、Token、密码或 OTP；
- 报表按公司、产品、部门、机构和时间范围隔离；导出内容默认脱敏并记录导出审计。

## 6. 审计与证据要求

### 6.1 必须记录的事件

- 登录成功/失败、退出、会话撤销、密码重置、员工启停用、角色/部门/机构变更；
- 客户和 KYC 新建、提交、补件、审核、退回、拒绝、字段修改、附件上传/扫描/删除；
- 产品/费率/逾期规则/语言/通知模板/分单规则变更；
- 贷款状态流转、审批、复核、签约、放款、提现、还款、冲正、退款、对账；
- 每日/月度放款限额命中、监管资金余额跌破 20% 预警线、风险策略切换、人工冻结/解除、告警确认和风险事件关闭；
- API 调用失败、权限拒绝、重复请求、外部机构回调、Bot 切换和系统安全告警；
- 管理员查看敏感字段、下载附件、导出报表和查看审计记录。

### 6.2 审计字段

每条记录至少包含：事件 ID、公司 ID、对象类型/对象 ID、动作、结果、操作者员工 ID/角色、前后值摘要、原因、请求 ID、关联业务 ID、时间、IP/设备摘要、来源域名和版本号。密码、Token、OTP、完整身份证号和完整附件内容不得写入审计日志。

### 6.3 不可抵赖与留存

- 审计只追加，不允许普通员工删除或覆盖；
- 关键记录使用哈希链/不可变存储或定期归档校验；
- 线上审计保留期、归档期和删除策略需由合规负责人确认；
- 审计导出采用脱敏副本，导出动作自身也写入审计。

### 6.4 资金监管与风控事件

- 资金监管使用独立风险事件类型 `funding_regulatory_warning`，不得只写一条普通日志；
- 风险事件状态至少包括 `open`、`acknowledged`、`mitigating`、`resolved` 和 `closed`，每次状态变化都要记录操作者和处理依据；
- 事件快照至少保存：监管资金池 ID、配置版本、预警比例、触发时余额、当日/当月累计放款、公司时区、触发时间、影响范围和当前放款策略；
- 20% 预警默认只触发告警；若风控策略配置为“预警即冻结”，服务端必须在放款事务中阻断新放款，并要求有权限的管理员/财务复核员双人解除；
- 解除冻结前必须完成余额核对、流水对账和原因填写；不得通过修改累计金额或删除流水消除预警；
- 风险事件、审计事件和资金流水使用同一 `request_id`/`correlation_id` 串联，支持按公司、资金池、流水号、Loan ID 和时间范围检索。

## 7. 安全配置要求

### 7.1 身份与会话

- Mini App 只接受服务端验证的 Telegram `initData`；H5 手机验证码会话与后台员工会话完全隔离；
- 后台员工会话 8 小时有效，HttpOnly、Secure、SameSite；退出立即撤销；
- 公司、成员权限版本、密码版本、分单版本变化使旧会话失效；
- 登录尝试、验证码、敏感 API 和文件上传均有速率限制；
- 生产关闭 demo 登录、测试账号、测试资金和调试输出。

### 7.2 密钥与外部服务

Bot Token、Telegram Gateway Token、支付网关密钥、Google Geocoding Key、数据库 URL、Cookie secret 只放 VPS/平台 secret；不进入源码、前端构建、日志、截图或导出文件。

### 7.3 文件与输入安全

- 仅允许声明的图片/PDF，服务端以文件头和 MIME 双重判断；
- 限制 10MB（或当前明确的更低限制），代理、应用和扫描服务限制必须一致；
- 生成随机对象名，拒绝 `../`、绝对路径和用户可控扩展名；
- 同一业务字段的内容哈希用于检测重复上传，但不能把哈希当作授权；
- 上传成功必须经过扫描和元数据校验，扫描失败按拒绝处理；
- 文本输入做长度、字符集、格式和业务范围校验，不能只依赖前端。

### 7.4 数据库安全

- 所有核心表带公司/租户范围或通过关联表强制隔离；
- 身份证号、手机号、银行资料、签名和附件引用加密或脱敏存储；
- 金额使用整数最小货币单位；流水和账单禁止浮点计算；
- 迁移可重复执行并在测试、预发布、生产分别验证；
- 备份加密、定期恢复演练、最小数据库账号权限和连接审计必须落地。

## 8. 技术边界与接口约束

### 8.1 前端边界

前端只负责页面状态、表单交互、语言、加载和错误展示；不保存 Bot Token/支付密钥，不决定权限，不生成最终账务结果，不直接拼接 SQL，不把客户全量数据放入浏览器存储。

### 8.2 API 服务边界

API 负责认证、RBAC/数据范围、字段校验、状态机、幂等、事务、审计和外部回调验签。所有写操作返回稳定错误码、request ID 和可翻译消息键；敏感错误不泄露数据库、路径或密钥细节。

### 8.3 数据库边界

建议按领域拆分客户、KYC、贷款申请、合同、账单、资金分录、通知、任务、审计、员工权限和分析事件。历史合同/费率/规则使用快照；不要依赖修改后的当前配置回算历史业务。

### 8.4 异步任务边界

提醒、逾期计算、Bot 重试、文件扫描、外部机构回调、报表聚合由后台任务处理，要求可重试、幂等、失败队列和告警。不能用浏览器定时器承担生产任务。

### 8.5 持牌机构独立服务器边界

- 持牌机构后台、机构数据库、文件和任务服务部署在机构独立服务器或独立云账号/网络中；
- 金融服务机构只能通过机构公开 API 或专线/VPN 访问约定接口，不得 SSH、直连数据库或读取机构文件目录；
- 机构内部员工、角色、审批记录和许可证资料由机构自行管理，金融服务机构只保存必要的外部引用和回执；
- 机构服务器必须具备独立备份、监控、访问控制、密钥管理、漏洞修复和应急下线能力；
- 机构服务不可用时，申请进入“机构待处理/接口异常”状态，不能由客户端或运营人员伪造审批成功。

### 8.6 开放 API 独立系统后台

金融服务机构只传递机构必要字段和版本化业务请求；持牌机构返回审批/复核/放款结果及签名、时间和关联号。双方不得共享对方内部员工、数据库或未授权 KYC 全量资料。

开放 API 后台至少包括：

- 应用注册、机构/租户绑定、环境（Sandbox/Production）和应用状态；
- API 产品目录、版本、权限 Scope、字段级脱敏和变更公告；
- API Key/OAuth 客户端生成、只显示一次、轮换、吊销和过期策略；
- IP 白名单、来源校验、请求签名、时间戳/Nonce、防重放和幂等键；
- 每个应用的配额、并发、速率限制、错误率、延迟和调用量报表；
- Webhook 地址、事件订阅、回调签名、重试队列和死信记录；
- 沙箱数据与生产数据完全隔离，测试凭据不可访问真实客户或真实资金；
- 开发者文档、OpenAPI 定义、示例请求、错误码和变更历史。

API 后台只管理接口接入和技术治理，不替代业务后台的 KYC 审核、贷款审批或财务复核权限。任何 API 调用都必须再次执行公司/机构范围、业务状态、字段权限和幂等校验。

### 8.7 部署边界

- Caddy/Nginx 只做 TLS、路由和基础限制，不承担业务授权；
- `app-payease`、开放 API 网关、API 控制台、文件扫描器、ClamAV、数据库和任务服务分离；
- 持牌机构服务器与金融服务机构服务器分离，生产网络只开放必要 API 端口；
- 发布前备份当前版本和迁移状态，发布后检查容器健康、域名 HTTPS、Mini App/H5/后台登录、API 关键接口和 5xx/502；
- 任何“部署完成”必须同时有进程/容器状态和外部访问验证。

## 11. 验收清单

- [ ] 一个新员工只能看到被分配的公司、部门或机构数据；
- [ ] 员工停用、改角色或重置密码后旧会话立即失效；
- [ ] KYC 客服修改一位数字能看到前后值、原因、复核人和时间；
- [ ] 同一个申请不能由同一人完成审批和复核/放款确认；
- [ ] 费率修改不会改变历史合同、账单和分录；
- [ ] 重复支付/还款请求不会重复入账；

- [ ] 监管资金余额达到 20% 预警线会生成风控事件、审计记录和通知；

- [ ] 上传恶意文件、伪造扩展名、超限文件、路径穿越和重复上传均被拒绝；
- [ ] 10MB 限制在浏览器、反向代理、API、扫描器和存储层一致；
- [ ] 所有关键动作可按用户、申请、Loan ID、流水号和 request ID 追溯；
- [ ] 审计导出不含密码、Token、OTP、完整证件号和未授权附件；
- [ ] `khmerx.org`、`payease.khmerx.org`、`admin.khmerx.org`、`api.khmerx.org` 的路由、HTTPS、CORS/CSP 和 Cookie 范围符合设计；
- [ ] Mini App 自动登录、H5 验证、后台员工登录三套身份不能相互越权；
- [ ] 生产环境关闭测试资金、demo 登录和调试错误；
- [ ] 容器健康、备份恢复、5xx/502 告警和回滚流程完成一次演练。

## 12. 产品决策记录

1. 面向全部社会用户，不把工厂/企业审核设为默认前置环节。
2. Telegram Mini App 和 H5 统一使用 `payease.khmerx.org`；后台使用 `admin.khmerx.org`。
3. 后台三语保留中文、English、高棉语切换；客户端按语言策略可关闭中文。
4. 客服修改 KYC 不是通用员工权限，必须单独授予、记录前后值并支持复核。
5. 当前系统的资金和外部通知属于测试/模拟范围，真实金融能力必须通过独立适配层和上线评审进入。
6. 持牌机构使用独立服务器和独立网络边界；开放 API 使用独立系统后台管理，不与业务后台共用员工权限或数据库直连。

## 14. 应急处理与受控纠错机制

“不通过绕权方式改写核心数据”不等于没有应急处理。系统必须提供正式的 Break-glass 应急流程，所有紧急操作都通过受控 API、临时权限和补偿记录完成。

### 14.1 可启动应急处理的场景

- 放款、还款、回调或对账处于未知状态，需要核对或重试；
- 重复请求、部分成功、账务不平或资金监管预警导致业务阻断；
- KYC 关键字段错误、附件误绑定、错误分单或投诉要求立即纠正；
- 外部持牌机构、支付通道、Telegram Bot 或数据库短时不可用；
- 安全事件、越权访问、敏感资料泄露或需要紧急冻结账户。

### 14.2 应急流程

```text
发现异常
→ 创建应急事件
→ 自动保存当前快照并关联 request_id / Loan ID / 流水号
→ 评估影响范围与临时风险等级
→ 授予最小范围、最短时效的应急权限
→ 双人复核后执行受控补偿动作
→ 对账、重放或补件验证
→ 撤销应急权限
→ 关闭事件并形成复盘报告
```

### 14.3 应急权限和操作边界

- 应急权限默认 30 分钟有效，必须指定对象、动作、原因和失效时间；超时自动失效；
- 发起人和复核人必须是不同员工；涉及资金、放款冻结解除、账务冲正或 KYC 关键字段时必须由管理员/财务复核员或 KYC 审核主管双人确认；
- 原始资金流水、已签合同、审批结果和审计记录不可覆盖或删除；账务纠错使用冲正/补偿分录，KYC 纠错使用新版本和前后值审计；
- 外部回调未知状态不得直接标记成功，必须执行状态查询、幂等重试或进入人工核对队列；
- 应急权限不能扩大员工原有公司、部门、机构或字段范围，只能临时允许指定对象的指定动作；
- 所有应急查看、下载、修改、冻结、解除、重试和导出动作均写入不可变审计。

### 14.4 应急事件记录

应急事件至少保存：事件编号、事件类型、影响公司/机构、关联客户/申请/Loan ID/流水号、发现时间、影响范围、风险等级、发起人、复核人、临时权限、前后快照、执行动作、对账结果、恢复时间、关闭原因和复盘结论。

应急处理完成后，系统必须检查：资金分录是否借贷相等、累计放款限额是否正确、资金监管余额是否重新计算、客户状态是否可解释、通知是否需要补发，以及所有外部机构回执是否已闭环。
