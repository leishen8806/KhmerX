# KYC 交互与体验评审（2026-10-23）

评审基线：`main` 839f101（等同 PR63 f2b5993 的 KYC 代码）。
范围：客户端 KYC 填写（H5 / Telegram Mini App，`app/kyc/client.tsx`、`components/mini-client.tsx`），以及员工端审核（`/kyc/review`，团队工作台的「KYC 审核订单」`components/kyc-orders.tsx`）。
方法：逐行阅读代码，对照线上 `/kyc/review` 与 `/h5/kyc` 入口实际渲染。线上没有执行任何写操作。Flutter App 的 KYC 不在本次范围。

## 总体判断

功能和数据规则已经比较完整：草稿、补件、版本、加密、审核留痕都有。主要问题是**同一个组件同时服务客户和审核员**（`KycClient review={true|false}`），结果两边都不顺手：

- **客户端**：把内部和测试信息（表格权重、单元格来源、KESS 未接入、模拟会话）直接展示给客户；校验只在点「下一步」时以弹出提示统一报错；上传没有拍照入口，也没有预览；文案基本只有中文，而目标客户在柬埔寨。
- **审核端**：审核员要像客户一样逐步点击 7 个分区，后面的分区默认锁定；材料只能在新标签页里逐个打开；核对勾选与内容分离；补件原因是自由文本，客户端靠正则去猜要跳到哪一步；没有版本差异；队列看不到等待时长和负责人。

## 三、跨端和技术层面的建议

1. **拆分组件**：把 `KycClient` 拆成 `CustomerKyc` 和 `KycReview` 两个组件，共享 `lib/kyc/core.ts` 里的字段、校验和材料规则。目前一个 1600 行的文件里遍布 `review ? … : …` 分支，这也是两端体验都受限的根本原因。
2. **结构化补件协议**：审核结果在现有的 `checklist` 之外增加 `requests: [{ target: "field:documentNumber" | "slot:idFront" | "section:contacts", reasonCode, note }]`。客户端据此定位和标记，替代 `supplementStep` 的正则匹配。需要同步更新 Flutter 契约（`76-P2-kyc-contract.md`），保持向后兼容：旧数据仍按 checklist 处理。
3. **埋点**：现在已有 `kyc_step_view`、`kyc_step_complete` 和上传相关事件。建议补充 `kyc_field_error`（字段 id、错误类型）、`kyc_submit_blocked`、`kyc_review_decision_time`（从打开到做出决定的时长），用来衡量改版效果。
