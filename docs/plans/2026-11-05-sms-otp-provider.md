# 正式短信 OTP 接入设计（H5 与 App）

状态：设计评审稿，仅包含方案与验收计划，不包含实现代码

日期：2026-11-05

## 1. 背景与目标

当前手机号登录的验证核心位于 `lib/h5-auth-core.ts`。现有 `demo` 和 `telegram` 模式分别用于测试验证码与 Telegram Gateway；手机号登录的发送、校验、浏览器绑定、挑战过期和失败次数已经有可复用的抽象。App 目前也使用手机号 + 验证码界面，但正式上线前，H5 与 App 必须统一接入短信 OTP，不能依赖 demo 验证码或 Telegram 文案/通道。

本设计的目标：

1. 增加一个明确的 `sms` 认证模式，向 H5 与 App 提供同一套手机号 OTP 合约。
2. 短信供应商只负责发送和返回供应商请求标识；验证码生成、哈希保存、有效期、消费和失败策略由业务侧控制。
3. 同时按手机号、IP、浏览器和租户实施频率限制，避免枚举、刷短信和验证码猜测。
4. 在灰度可验证、可回滚；生产配置启动时不得意外启用 demo 或缺少短信密钥。

非目标：本阶段不改资金、放款、KYC、团队权限或数据库迁移；不在文档中决定供应商或承诺具体价格、到达率、合同条款。

## 2. 供应商评估候选

以下是需要业务和技术共同评估的候选类别，不是采购结论。实际可用性必须用柬埔寨目标运营商、真实 `+855` 号码和合规审核确认；本文不填写未经报价单确认的价格或到达率。

| 候选 | 需要核实的维度 | 选择风险/备注 |
| --- | --- | --- |
| Twilio Programmable Messaging / Verify | 柬埔寨及目标运营商的到达率、是否支持并稳定接收 `+855`、API/Verify 能否返回请求 ID、发送者 ID、合规材料、数据驻留、停用/退订能力 | 国际平台接入快，但目的地覆盖、发送者注册和内容限制必须先做运营商实测 |
| Vonage Verify / SMS API | `+855` 覆盖、Verify 生命周期与重试语义、API 认证方式、发送者要求、合规与数据处理协议 | 需确认 Verify 产品在目标目的地的可售性，不以其他国家经验推断 |
| Infobip Verify / SMS | 目标运营商路由与 DLR、`+855` 支持、API/Webhook、发送者 ID、合规与审计导出 | 企业路由和本地支持可能有优势，须取得正式覆盖和报价 |
| Sinch Verification / SMS | `+855` 实际送达、验证 API 的挑战状态、API 密钥管理、发送者 ID、合规要求 | 需比较 Verify 产品与普通 SMS 的重试、计费和风控差异 |
| MessageBird/Bird Verify 或同等 CPaaS | 目的地覆盖、`+855` 号码策略、API 稳定性、Webhook 签名、合规和数据处理 | 产品名称、覆盖和定价会变更，采购前必须重新核验 |
| 柬埔寨本地运营商或持牌 SMS 聚合商 | 与 Smart、Cellcard、Metfone 等目标网络的直接到达率、`+855` 发送者登记、API 形式、合同/监管要求、数据处理和 SLA | 可能有更好的本地路由，但需审查供应商资质、备援能力和开发者接口 |

统一评估表必须至少记录：

- 分运营商、时段、语言和消息模板的送达率与延迟 P50/P95；不能只记录供应商后台的 accepted。
- 目标号码是否接受 `+855`，是否要求 alphanumeric sender ID、短码或预注册模板。
- API 的认证、超时、幂等键、请求 ID、状态查询/DLR、错误码、重试和 webhook 签名。
- 合规、隐私、数据保留、跨境传输、内容审查、退订和滥用申诉流程。
- 账单、配额、突发限流、SLA、支持响应和故障时的备用路由。

## 3. 认证模式与配置边界

### 3.1 模式

在设计层面将 `AuthMode` 扩展为 `demo | telegram | sms`。本 PR 不实现该扩展；实现 PR 必须保持现有模式兼容，并将 `sms` 作为正式手机号模式。

正式配置使用 `PAYEASE_H5_AUTH_MODE=sms`。若 App 与 H5 共用认证核心，App 的渠道 runtime 也必须解析为 `sms`，不能由客户端传入任意模式覆盖服务端配置。

### 3.2 密钥和启动校验

- 供应商 API key、API secret、签名密钥只放在部署平台的加密 Secret/环境变量中，或本地 `.dev.vars`；`.dev.vars` 必须被 `.gitignore` 忽略，绝不提交、打印、写入截图或审计事件。
- 需要的配置至少包括：`PAYEASE_H5_AUTH_MODE`、`PAYEASE_SMS_PROVIDER`、供应商密钥、发送者 ID/号码（如供应商要求）、环境名和短信模板版本。
- `PAYEASE_H5_AUTH_MODE=sms` 启动时必须校验：供应商白名单有效、必要密钥非空且达到供应商要求的最小长度、发送者配置完整、环境为允许短信的 local/gray/production、数据库绑定存在、回调签名配置（若采用 DLR webhook）完整。校验失败必须拒绝启动并给出不含密钥的配置错误。
- `demo` 只允许 local 或明确隔离的测试运行时；生产配置、灰度公网配置和 `sms` 配置不得同时设置 demo 放行开关。`allowDemo` 不得由全局 `KHMERX_TEST_MODE` 推导，避免意外放宽 MFA、双人审批、病毒扫描、密码发放等安全门。
- 生产环境若设置仅用于演示的 OTP 开关，`assertProductionSafe()` 必须直接失败；启动日志只记录配置名和布尔状态，不记录密钥值。

### 3.3 供应商适配层

业务核心只依赖窄接口，供应商 SDK 或 HTTP 细节留在适配层：

```text
SmsProvider.send({destination, template, requestId})
  -> {providerRequestId, acceptedAt}
SmsProvider.status({providerRequestId})
  -> {state, deliveredAt?}       # 仅用于观测，不决定 OTP 正确性
```

适配层负责超时、响应 schema 校验、供应商错误归一化和敏感字段清理。业务层不得把供应商的号码存在与否、具体错误或原始响应返回给客户端。

## 4. 发送与校验流程

### 4.1 发送接口

沿用现有 H5 接口路径，新增 `sms` 模式实现，不新增客户端私有接口：

- `POST /api/h5/auth/send`：输入规范化后的手机号、同意接收验证码和 purpose（login/reset）。
- 服务端确认渠道、注册策略、浏览器 token、CSRF/来源约束和频率限制后，生成挑战 ID。
- 服务端使用 CSPRNG 生成 6 位 OTP，仅在内存中短暂存在，立刻使用服务端 pepper/HMAC 做哈希后写入挑战记录；数据库不保存明文 OTP。
- 写入挑战记录后调用短信供应商。挑战状态先为 `sending`，供应商接受且响应 schema 通过后改为 `ready`；失败则标记 `failed` 并消费该挑战，不自动回退到 demo 或 Telegram。
- 客户端只收到挑战 ID、脱敏手机号、过期时间、重试时间和稳定的通用提示；响应绝不包含 `demoCode`、供应商错误、是否注册或电话号码存在信息。

### 4.2 校验接口

- `POST /api/h5/auth/verify`：输入挑战 ID 和 6 位数字 OTP。
- 服务端校验挑战属于当前租户、浏览器绑定、purpose、模式、未消费、未锁定且未过期。
- 使用固定时间比较校验输入 OTP 的 HMAC 哈希；失败增加 attempts，达到上限锁定/消费挑战，返回稳定错误。
- 成功时以原子条件更新 `consumed=1` 和 `status=used`，再创建或更新手机号已验证会话。重复提交必须失败。
- App 使用同一业务语义；客户端只负责收集手机号/OTP，不决定认证模式、TTL、是否跳过验证或回退路径。

### 4.3 时间和状态

- OTP 有效期沿用短时挑战设计，建议默认 5 分钟；由配置常量控制并在灰度通过后冻结。
- 同一手机号在重发时，旧挑战立即置为 `replaced`；只能使用最新的 `ready` 挑战。
- 短信 accepted、delivered、failed 仅作为运营观测，不把 DLR 当作 OTP 校验结果。
- 供应商超时、限流、5xx、签名无效、响应字段不全统一为通用不可用错误；不得尝试另一个通道来掩盖失败。

## 5. 风险控制与审计

频率限制至少按下列维度分别计数，并组合使用：

| 维度 | 典型窗口/目的 | 备注 |
| --- | --- | --- |
| 手机号哈希 | 每小时发送次数、短重发间隔 | 只存 HMAC 后的稳定 key，不存明文手机号用于限流 |
| 浏览器 token | 发送和校验次数 | 绑定挑战，防止换浏览器接管 |
| IP/网段 | 短窗发送、校验和失败次数 | 处理代理头时只信任受控边缘；不把任意 `X-Forwarded-For` 当真实 IP |
| 租户/公司 | 总发送量和并发 | 防止单一公司拖垮供应商额度 |
| 账户/设备（如 App 可用） | 验证失败和设备异常 | 只做风控信号，不泄露手机号是否存在 |

具体阈值必须以灰度压测和供应商配额为依据，写入配置并可审计；超过限制返回 `429` 与 `Retry-After`，不泄露命中的是哪一个维度。

每次发送、校验成功/失败、挑战替换、供应商失败和配置拒绝写入审计事件，至少包含：租户、匿名化浏览器/IP 哈希、挑战 ID 的不可逆摘要、模式、purpose、结果、错误类别、时间、供应商 request ID 摘要和规则版本。禁止写入 OTP、API key、完整手机号、供应商原始响应或 `demoCode`。

## 6. 注册策略和接口安全

- `sms` 渠道注册必须先完成 `/verify`，再创建或恢复会话；不能因为 registration policy 默认值允许 `register` 就跳过手机号验证。
- `registerPhone` 的手机号输入只能用于规范化和查找，不得单独授予既有账号访问权；旧账号必须要求验证码或已设置密码。
- 登录、重置密码、设置密码的 policy 分支要分别测试；短信验证成功只授予任务限定的会话能力，不自动授予高风险操作权限。
- 任何短信发送失败、供应商未知状态、挑战不存在、哈希不匹配和超过尝试次数都必须失败；禁止回退到 demo、Telegram 或仅手机号登录。

## 7. 测试计划

### 单元与集成

1. OTP 生成使用 CSPRNG；数据库只出现 HMAC/哈希，不出现明文或响应中的 demoCode。
2. 正确 OTP、错误 OTP、过期、重发替换、重复消费、锁定、浏览器不匹配、租户不匹配和 purpose 不匹配。
3. 供应商 accepted、timeout、5xx、格式错误、限流和 webhook 签名错误；所有失败均不回退。
4. 按手机号、IP、浏览器、租户的各项限流及 `Retry-After`；并发条件下只允许一次消费。
5. `PAYEASE_H5_AUTH_MODE=sms` 的启动正例；缺密钥、非法 provider、生产演示开关、缺数据库绑定的启动反例。
6. `KHMERX_TEST_MODE=false` 下 MFA、双人审批、病毒扫描、密码发放等安全保护仍然开启。
7. H5 与 App 均须验证：未输入 OTP 不能登录，输入测试环境约定的 `123456` 只能在隔离测试/灰度 demo 适配器中生效；正式 `sms` 模式不得接受固定 OTP。
8. 三语言和错误文案不能暴露号码存在性、供应商信息或密钥。

### 门禁和证据

- TypeScript 单元/集成测试、类型检查、分离构建和 lint 必须通过。
- Flutter analyze/test 必须通过，覆盖 App 手机号发送/输入/错误/成功页面。
- 使用 `+855` 测试号码时只保存脱敏截图和结果摘要；不把真实号码、OTP 或供应商密钥写入仓库。
- 记录每个供应商候选的测试批次、网络、运营商、时间窗和聚合结果；不能用单次 accepted 代替实际送达结论。

## 8. 上线步骤与回滚

1. 供应商评估、合规和合同确认；确认 `+855` 发送者登记与配额。
2. 先交付配置校验和适配器接口，再交付核心 `sms` 模式，最后交付 H5/App 客户端切换；每个 PR 保持可回滚。
3. 在 local 用 fake provider 验证完整状态机；在 gray 用真实但受限的供应商账户和内部测试号码验证送达、延迟、错误、限流和审计。
4. 灰度入口默认关闭公开注册；小比例、白名单租户启用 `PAYEASE_H5_AUTH_MODE=sms`，观察成功率、失败类别、延迟、重发率、供应商额度和安全告警。
5. 通过验收后再由负责人安排生产变更。生产部署不属于本设计 PR 的授权范围。

回滚优先级：先将灰度租户切回经过启动校验的既有安全模式（或关闭入口），再撤销短信发送配置；不要删除挑战/审计数据。若短信供应商故障，保持发送失败并提示稍后重试，不能静默降级到 demo/Telegram 或手机号直登。供应商密钥轮换和撤销按平台 Secret 管理流程执行。

## 9. PR 拆分计划（每个约 400 行以内）

1. **PR-A：配置与 provider contract**：`sms` 配置 schema、启动校验、Secret 读取、窄 provider 接口、fake provider 和配置失败测试；不切换默认模式。
2. **PR-B：发送与挑战存储**：OTP 生成/HMAC、挑战状态、发送适配器、过期/替换/失败和手机号/IP/浏览器/租户限流；补单元与集成测试。
3. **PR-C：校验与会话 policy**：`/verify` 原子消费、失败锁定、注册 policy 必须验证、审计事件和错误归一化；补并发/重放测试。
4. **PR-D：H5 客户端切换**：仅在服务端 runtime 宣布 `sms` 时展示短信流程，更新错误/加载/重发状态和三语文案；补 Playwright/接口合约测试。
5. **PR-E：App 客户端切换**：复用手机号 OTP 合约，补 Flutter 页面和测试；不在客户端保存密钥或决定模式。
6. **PR-F：灰度 runbook 与观测**：供应商指标、脱敏审计、灰度开关、验收记录、回滚清单和告警；不包含部署执行。

每个 PR 合入前必须核对完整 diff、相关门禁和未改动安全边界；任何包含数据库迁移、部署配置或生产变更的后续 PR 另行按负责人审批。
